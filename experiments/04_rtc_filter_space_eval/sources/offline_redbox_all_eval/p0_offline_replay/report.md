# P0 오프라인 비교 — Redbox 20k 추론 방식과 후처리 (2026-10-19)

대상: `redbox_all/train/32_20000/pi05_expert_bs32_20k/checkpoints/020000` (pi05, chunk 50, expert만 학습), lerobot 0.6.2.
지키며 진행한 조건: 로봇 실행 없음, PID·캘리브레이션 변경 없음, max_relative_target=8 변경 없음, 데이터셋·체크포인트 수정 없음, 재학습 없음.

> ## ⚠ 이 결과의 한계
> - **열린 루프(open-loop) 재생입니다.** 녹화된 관측을 시간 순서대로 넣었습니다. 시뮬레이션한 명령이나 필터가 로봇 자세를 바꿔도 다음 관측은 바뀌지 않습니다.
> - 그래서 **실제 성공률과 안전성은 이 결과로 확정할 수 없습니다.** 설정 간 상대 비교로만 써야 합니다.
> - 추종 오차와 clamp는 rollout 데이터로 맞춘 서보 모델로 "이 명령을 따라갔다면"을 추정한 값입니다.
> - 사람 조작 에피소드를 재생할 때는 관측이 사람 궤적을 따르므로, 정책 계획과 어긋나 경계 점프와 clamp가 부풀려집니다.
> - ramp는 다음 추론의 state를 "현재 chunk 마지막 목표값"으로 바꿔 넣기 때문에, 열린 루프에서 이미지(실제 팔)와 state가 서로 모순됩니다. ramp의 파지 오차 값은 신뢰하기 어렵습니다.

## 1. 방법

### 재생 데이터
- **rollout 재생**: 실제 실패한 rollout(2,404프레임, 영상 포함). 녹화 프레임에는 추론으로 멈춘 시간이 빠져 있으므로, sync의 멈춤 동안에는 관측을 진행시키지 않았습니다.
  - 검증: 이렇게 하면 sync 재생의 추론 횟수가 49번으로, 실측 48번과 맞습니다.
- **사람 조작 6편**: 6개 그룹에서 그룹 중앙값 길이에 가장 가까운 1편씩입니다(ep 18, 70, 172, 202, 264, 350). 파지 순간 12번이 들어 있어, 사람 action을 정답으로 파지 자세와 그리퍼 타이밍을 평가합니다.

### 추론 방식 (모두 lerobot 0.6.2의 실제 정책·전처리·후처리 코드)
- **sync**: `SyncInferenceEngine`과 같습니다. 50개를 다 쓰면 추론하고, 추론 시간 동안 새 명령이 없습니다.
- **RTC**: 단순히 저장된 action을 이어 붙인 것이 **아닙니다.** `_rtc_loop`의 결정 로직을 그대로 재현했습니다.
  - 실제 클래스와 함수를 그대로 호출: `ActionQueue`(merge, get_left_over, 지연만큼 앞부분 버리기), `LatencyTracker`(첫 추론 제외, max 기반 지연 추정), `_estimate_rtc_delay`, `_normalize_prev_actions_length`, `policy.predict_action_chunk(inference_delay, prev_chunk_left_over)`(guided denoising).
  - 백그라운드 스레드만 결정적 시뮬레이션 시계로 대체: 큐가 `queue_threshold`(30) 이하이면 그 틱의 관측으로 추론 시작 → 측정한 실제 추론 시간만큼 틱이 지나는 동안 큐에서 계속 소비 → 끝난 틱에 merge.
- **ramp**: jinnymo/VLASH 방식. chunk 끝 8틱 전에 다음 추론(state ← 현재 chunk 마지막 action), 전환 때 8개를 `w=(i+1)/(n+1)`로 섞습니다. 원 사례는 n_action_steps 20, 우리는 50으로 시험했습니다.

### 지연
- 각 추론의 벽시계 시간(전처리+추론+후처리)을 실제로 재서 틱으로 환산했습니다.
- **현실 지연(×1.55)**: 이 Jetson의 실제 cubemark RTC 기록이 p50 0.31–0.32 s, delay 10–12틱으로, 오프라인 측정(0.20 s)의 1.55배였습니다.
- **스파이크 스트레스**: 40번째 추론마다 지연 ×2.5. 실제 기록에서 0.7–0.8 s 스파이크는 첫 추론에만 있었고, 첫 추론은 추적에서 제외되므로 이 시험은 실제보다 비관적입니다.

### 난수
- 추론 호출 순번 k마다 `torch.manual_seed(1000+k)`. 같은 방식이면 같은 노이즈입니다.
- 방식마다 추론 시점과 횟수가 다르므로(sync 49번, RTC 120번) 방식 간 노이즈는 완전히 같을 수 없습니다.

### 후처리 필터 (엔진 출력 → 필터 → 로봇. RTC 큐와 leftover는 필터 전 값 = PR #3893 위치)
- `ema25`: α 0.25, 관절별로 10° 넘게 벌어지면 통과 (PR 기본값)
- `vc_pr`: 프레임당 1.25° 제한 (PR 기본값)
- `vc_tel`: 관절별 사람 조작 action 변화량 p99.5 = [2.46, 4.13, 4.22, 4.57, 3.43, 4.47]°/프레임
- `ema50vc_arm`: 팔 5관절만 α 0.5 EMA, 그리퍼는 그대로, 그 뒤 vc_tel

### 서보 모델 v2 (관절별: 지연 d, 방향별 이득, 속도 포화, 8° clamp 포함)
- rollout 앞 60%로 맞추고 뒤 40%로 자유 실행 검증했습니다.
- 검증 RMSE(°): pan 0.36, lift 3.21, elbow 1.92, wrist_flex 0.85, wrist_roll 0.51, gripper 0.57
- 실제 rollout action에 적용하면 clamp 26.6%로, 실측 28.8%와 비슷합니다.
- lift는 이득이 탐색 범위 끝(0.6)에 걸려 있어 정밀도가 낮습니다.

## 3. 해석

1. **chunk 안 잡음(문제 1)**
   - 모든 방식에서 남습니다. RTC 5 스텝은 sync 10 스텝 대비 약 −28%(0.86→0.62°)입니다.
   - 팔 관절 EMA까지 더하면 −48%(0.45°)가 되고, 지연 1프레임, 파지 오차 +0.04°입니다.
   - 그래도 사람 조작(0.25–0.5°)의 위쪽 끝 수준입니다. 학습된 모델 자체의 잡음이라 추론 쪽에서 완전히 없앨 수는 없습니다.
2. **경계 불연속과 추론 지연(문제 2)**
   - sync는 명령 없는 틱이 14–20%입니다.
   - RTC는 이 비율을 0.3%로 줄입니다.
   - 경계 점프는 **execution_horizon이 실제 지연(10–12틱)보다 넉넉히 클 때만** 줄어듭니다. h10은 현실 지연에서 sync보다 나쁩니다.
   - h30은 잡음은 줄지만 반응이 늦어 파지 오차가 커집니다(7.6–9.6°). **h20 EXP 5 스텝**이 균형점입니다.
3. **파지 정확도와 그리퍼 타이밍**
   - RTC는 약 20틱마다 새 관측으로 다시 계획합니다. 그래서 sync보다 파지 오차(6.1° 대 11.5°)와 그리퍼 시점차(18 대 25프레임)가 작습니다.
   - 그리퍼에 EMA를 걸면 시점차가 6프레임 늘어납니다. 그래서 그리퍼는 필터에서 뺐습니다.
   - 단, 모델 자체의 파지 오차(약 5–6°)는 남습니다. 이전 분석대로 파지 실패의 주원인입니다.
4. **PR #3794 기본값은 이 모델에 맞지 않습니다**
   - EMA 0.25 + 리셋 10: 지연이 쌓였다가 한 번에 따라붙어 8° 넘는 점프가 89번 새로 생깁니다.
   - 1.25°/프레임 제한: clamp는 0이 되지만 속도를 37.5°/s로 묶어 지연 2.6프레임, 파지 오차 +0.9°가 생기고 학습 분포보다 느려집니다.
5. **clamp는 추론 방식으로 거의 줄지 않습니다** (35% → 27%). 원인은 4절입니다.

## 4. clamp 분석 (실제 rollout, max_relative_target=8 그대로)

`clamp_runs.csv`, `clamp_summary.json`, `figE_clamp_servo.png`

- **규모**: |목표−실제| > 8°인 프레임 693/2404(28.8%), 관절별 clamp 구간 119개. lift 514프레임, elbow 356, wrist_flex 121, gripper 55, wrist_roll 20, pan 12.
- **시작 원인**: 목표값이 4° 이상 튀어서 시작한 구간 29개, 추종 지연이 쌓여서 시작한 구간 90개. chunk 위치 0–2에서 시작한 구간은 21개뿐입니다.
- **clamp 중 관절 상태**: 거의 모든 구간에서 관절은 1.7–2.4°/프레임으로 계속 움직였습니다. 멈춘 채 오차만 유지된 구간(테이블·박스에 닿았을 가능성)은 lift 8프레임뿐입니다.
  - 이 속도는 서보 모델의 `8° × k / (1 + 2k)` ≈ 1.6–1.9°/프레임과 맞습니다. **8° 제한이 사실상 관절 속도 상한(약 50–60°/s)으로 작동합니다.**
  - 정책이 그보다 빠른 동작을 지시하면 오차가 쌓입니다. 가장 긴 구간은 lift 71프레임에 최대 오차 44–48°였습니다.
- **참고**: 사람 시연은 이 제한 없이 녹화됐습니다. 지시에 따라 시연의 추종 오차 분포를 제한 완화의 근거로 쓰지 않았습니다.

### 제한값을 바꾼다면: 하드웨어 위험과 검증 방법 (이번에는 변경하지 않음)
- **위험**
  - 큰 목표 차이가 한 번에 서보로 전달되어 순간 전류와 가속이 커집니다(STS3215 과부하·발열).
  - 중력이 걸리는 lift에서 내려갈 때 과도 응답이 생길 수 있습니다.
  - 테이블·박스·자기 몸체와의 충돌 속도가 커집니다.
  - 정책이 잘못된 목표(예: ramp처럼 실제와 동떨어진 값)를 낼 때 막아 주는 장치가 약해집니다.
- **검증 순서(제안)**
  1. 오프라인에서 후보 제한별로 서보 모델 clamp, 최대 명령 속도, 최대 오차를 계산합니다.
  2. 정책 없이 미리 정한 느린 궤적으로 공중 자세에서 관절별 시험을 합니다. 전류·온도는 읽기만 합니다.
  3. 관절별 dict로 한 관절씩 완화합니다.
  4. 그다음에야 정책 시험을 합니다.
  - 모든 단계에서 비상정지를 준비합니다. 값은 사용자가 결정합니다.

## 5. 현재 Redbox 20k 모델에 가장 맞는 추론 방식

**RTC (guided), execution_horizon 20, schedule EXP, denoise 5, queue_threshold 30(기본)**
+ **후처리 ema50vc_arm** (팔 5관절 EMA α 0.5, 그리퍼 제외, 관절별 속도 제한 = 사람 조작 p99.5)

1. **명령줄만으로 가능한 단계 (코드 변경 없음)**:
   `--inference.type=rtc --inference.rtc.execution_horizon=20 --inference.rtc.prefix_attention_schedule=EXP --policy.num_inference_steps=5`
   - 현실 지연 기준: 경계 >8° 4번(최대 9.9°), 잡음 0.62°, 파지 오차 6.1°, 명령 없음 0.3%
   - 이전 cubemark 평가 설정은 LINEAR 기본값에 queue_threshold 40이었습니다.
2. **필터 추가 단계**: lerobot 0.6.2에 없어서 우리 wrapper(`rollout_logged.py`)에 구현해야 합니다. 아직 구현하지 않았습니다.
   - 현실 지연 기준: 경계 >8° 0번(최대 4.6°), 잡음 0.45°, 지연 1프레임, 파지 오차 6.1°, 그리퍼 타이밍 유지

## 6. 실물 재시험 전에 남은 위험

1. **열린 루프 한계**: 폐루프에서는 필터와 RTC가 바꾼 자세가 다음 관측을 바꿉니다. 수치는 상대 비교용입니다.
2. **clamp와 추종 지연이 그대로입니다** (27% 틱): lift·elbow가 빠른 동작에서 수십 도 늦게 따라갈 수 있고, 이 상태가 다음 관측이 됩니다. 추론 쪽으로는 해결되지 않습니다.
3. **파지 정확도**: 모델 자체의 파지 오차가 약 5–6°라 파지 성공은 기대하기 어렵습니다. 재시험은 진동 확인용입니다.
4. **지연 스파이크**: 실행 중간에 스파이크가 나면 lerobot은 최근 100회 중 최댓값으로 delay를 추정합니다. 그래서 약 1분 동안 RTC 이점이 줄어듭니다(스트레스 시험에서 경계 최대 32°). vc_tel이 프레임당 4.6°로 막아 주지만, 큰 차이를 빠른 경사로 바꿀 뿐입니다.
5. **필터 미구현·미검증**: wrapper 코드 작성과 오프라인 단위 시험이 먼저입니다. EMA 리셋 규칙 같은 세부 동작도 정해야 합니다.
6. **연산 부하**: RTC 5 스텝은 약 1.5회/s × 0.31 s로 GPU가 약 47% 바쁩니다. cubemark 실측에서는 29.9 Hz를 유지했습니다.
7. **서보 모델 정밀도**: lift 검증 오차가 3.2°입니다.
8. **재생 범위**: 재생은 T1 rollout 1편과 사람 조작 6편입니다. T2·T3 실물 상황은 들어 있지 않습니다.
