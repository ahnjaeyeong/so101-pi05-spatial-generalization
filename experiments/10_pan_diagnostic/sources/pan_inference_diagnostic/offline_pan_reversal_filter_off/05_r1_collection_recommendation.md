## 3. [해석]

- [해석] 현재 실패 (A0 · B1) 를 결정한 상태는 세 가지가 함께 있다.
  - 팔 접은 자세 (lift ≈ −100°)
  - pan 이 목표를 지나 한 방향으로 진행 중
  - 큐브가 손목 화면 위쪽으로 빠져 front 에만 보임
- [해석] 이 조합이 d2 에 0 편이다. 방안 A 로도 준비 단계에서 같은 조합을 만들면 직접 대응할 수 있다.
- [해석] 방안 A 의 약점은 '진행 중이던 속도 · prefix' 다. 모델 입력은 관측 1 프레임 + state 이고 (n_obs_steps 1), RTC prefix 만 과거를 담는다. 정지 상태에서 시작한 시연도 같은 관측 프레임을 만들 수 있다. 다만 실물에서는 RTC prefix 가 왼쪽 진행을 이어 붙인다 (03: index ≤ 19 목표 쪽 9.2 % → 0.5 %). 그래서 정지 상태 시연만으로 그 영향까지 덮이는지는 알 수 없다.
- [해석] 방안 B 는 상태 분포가 정확하다. 그러나 이 실패 유형의 빈도가 낮고 (2 / 20), 전환 안전 장치가 필요하다. 지금 바로 쓸 수 있는 것은 방안 A 다.

## 4. [제안]

1. **[제안] 1 차는 방안 A.** 현재 r12 R1 시나리오에 '팔 접은 자세' 조건을 넣는다:
   - R1-B2 (지나침) · R1-B3 (손목 놓침, front 보임) 의 시작 단계에 early (lift −95 … −103°) 를 추가한다.
   - pan 지나침 크기를 실패 범위로 넓힌다: 목표대 끝 기준 15 · 25 · 40° 이상. 지금은 15–25° 다.
   - 손목 상태를 '위 테두리로 빠짐' 과 '안 보임' 으로 나눈다.
   - 좌우는 둘 다 넣는다. 실패 2 건은 모두 왼쪽이고, 10 문서에서 왼쪽 need 의 첫 chunk 정지가 확인됐다.
   - 기록 필드 (pan_error_direction, wrist visibility, start lift) 는 이미 있다.
2. **[제안] 시작 상태 검증.** 수집 뒤 R1 시작 프레임의 (lift, pan − 목표, 손목 상태) 분포를 A0 · B1 의 over 상태 51 개 (02 문서) 와 비교한다.
3. **[제안] 방안 B 는 2 차.** 아래 순서로 별도 설계 · harness (가짜 팔) 검증을 먼저 한다. 실물에서 정책과 teleop 이 동시에 Follower 에 쓰는 구성은 만들지 않는다.
   - 정책 정지
   - queue 폐기
   - torque 유지 상태에서 Leader 정렬 확인 (차 ≤ 문턱)
   - 단일 writer 전환
4. **[제안] 평가 지표.** 같은 R1 상태 (오프라인 관측) 에서 U · G 의 실행 구간 목표 쪽 비율 (이 문서의 T4 지표) 을 학습 전후로 비교한다. 이 문서 수치가 기준값이다: U 7.7 %, G 4.3 %, 2,368 seed.
5. **[제안] RTC.** 데이터와 별개로 RTC 가 반전을 index ≤ 19 에서 억제하는 효과 (03) 가 있다. 새 데이터 학습 뒤에도 G 지표를 따로 본다.
